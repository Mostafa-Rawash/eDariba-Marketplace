# Statistics and Gamification Audit — eDariba Marketplace

Audit date: 2026-10-26. Read-only audit: no application code, DocType, configuration or existing documentation was changed. This file is the only deliverable.

## Executive summary

**Bottom line.** The marketplace collects only the raw records of its workflows: profiles, services, projects, proposals and requests, with a few timestamps. It computes almost no statistics from them. It has **no gamification at all** (no points, levels, achievements, challenges, leaderboards, reviews or reputation). The few numbers it shows are request counts by status, service and proposal counts, and a client-side profile-completion bar. Several trust signals shown to the public are **hard-coded or self-attested**, and those are the most urgent problems.

The only code executed during this audit was the 13 pure-Python unit tests (`request_rules`, `intent_router`), and they passed. No bench, test site or browser run was available. The 11 statistics and 3 gamification rows marked **Unverified** are complete in code across every layer and are the best candidates to become "Implemented" once they have been exercised on a staging site.

**Most important missing functionality**
1. **No event tracking of any kind.** Profile and service views, unique visitors, search impressions, clicks, search volume and no-result searches are not recorded anywhere. Every engagement, CTR and conversion metric depends on this.
2. **No reviews or ratings.** They were deliberately removed (`eDariba-Marketplace/docs/DOCTYPES.md:77,208`), so reputation, completed-engagement quality and client rating have no source data.
3. **No payments or transactions.** Revenue, earnings, refunds, spending and escrow have no backing data.
4. **No lifecycle timestamps** beyond `created_at`, `responded_at`, `submitted_at` and `published_at`. Response time, time to hire and completion rate cannot be computed reliably.
5. **No gamification data model, rules, ledger or UI.**

**Existing implementation that is incomplete or risky (P0)**
- **"Verified" can be set by the profile owner.** `MarketplaceProfile._guard_moderation_fields` explicitly allows the owner to move `Pending → Verified` (`eDariba-Marketplace/marketplace/marketplace/doctype/marketplace_profile/marketplace_profile.py:27-37`). `verification_status` sits at permlevel 0, and the `Invoicing Owner` role has permlevel-0 write (`marketplace_profile.json:172,236`). Verification therefore carries no moderation guarantee.
- **"Verified" badges are hard-coded in the app.** These places show "معتمد" / "معتمد من إي ضريبة" regardless of the data: `pre-edariba/src/marketplace/components/MpAccountantCard.vue:13-18`, `pages/requests/RequestNew.vue:59-60`, `pages/requests/RequestDetail.vue:158-159` and `pages/projects/SubmitProposal.vue:155-156`. The public site also shows hard-coded counters ("+٤,٢٠٠ محاسب معتمد", "+٨٥٠ باقة وفرصة", "100% مطابقة مصلحة الضرائب") and an "نخبة معتمد" tier derived only from self-reported years of experience.
- **The proposal status workflow cannot work for normal users.** `Invoicing Owner` has `write: 0` on Marketplace Proposal (`marketplace_proposal.json:114`). The app's shortlist, accept, reject and withdraw actions (`pre-edariba/src/marketplace/api/provider.js:304,357`) write through `/api/resource` and would be refused. The accept dialog also promises that other bidders are notified, the project closes and escrow protects the payment (`ProjectProposals.vue:169`). None of this exists in the backend.
- **Owner e-mail is likely exposed to guests.** The standard `owner` field is returned with Guest-readable profiles, services and projects through `/api/resource`, and `company` sits at permlevel 0 on the profile. The app relies on `owner` mirroring `user` (`pre-edariba/src/marketplace/api/docs.js:107-116`). Not executed; needs confirmation on staging.
- **Proposal metrics can be manipulated.** Nothing checks that the project is Published or open, and there is no proposal rate limit (`marketplace_proposal.py:9-46`). The front end maps backend messages that the backend never raises ("too many proposals", "not open for proposals", "verified professional profile", "cover letter must be"; `pre-edariba/src/marketplace/api/client.js:106-116`).
- **Business-data bug.** The public "عرض الخدمات (N)" count is capped at 20. It counts one page of `page_size: 20` (`edariba-theme/plugins/edariba-marketplace/includes/class-marketplace-repository.php:225-227`, used at `edariba-theme/themes/edariba-theme/marketplace/accountant-profile.php:21`).
- **The response timestamp is overwritten.** `responded_at` is rewritten on every reply edit (`eDariba-Marketplace/marketplace/api/workspace.py:226`), so "first response time" cannot be derived from it.

**Verified and unverified**
- *Executed:* `python -m unittest marketplace.services.tests.test_intent_router marketplace.services.tests.test_request_rules` ran 13 tests, all OK, in the eDariba-Marketplace repo.
- *Read but not executed:* every Python, JSON, Vue, JS and PHP file listed in §Scope. That includes the Frappe DocType tests, which need a bench. No live API, database, Qdrant or browser call was made, and production was not touched.
- *Documentation drift found:* `README.md` says a request recipient must be Verified and that `verification_status` is permlevel 1. The code does neither (`workspace.py:114-117`, `marketplace_profile.json`). The comments in `hooks.py:13-16` and `permissions.py:16-19` say normal users hold no DocPerm, but the DocType JSON grants `Invoicing Owner` permissions on Profile, Service, Project and Proposal (commit `e6a950a`).

## A. Statistics coverage by audience

- **Accountants / service providers.** Only operational counts exist: requests received by status (S-A19, code-complete), own services by status (S-B16, dev-only screen), public service count (S-A07, buggy cap). Profile completeness is client-side and dev-only. There is no engagement data (views, impressions, CTR), no quality data (ratings, response rate or time) and no money data. Trust signals are the weakest part: verification is self-attested and shown unconditionally, and availability and tier labels are hard-coded.
- **Freelancers.** Proposal counts by status exist in a dev-only panel (S-E03) and depend on a status workflow that normal users cannot drive (S-C10–S-C13, S-E04). Nothing about earnings, completion or acceptance rate exists.
- **Clients.** A client sees the requests they sent by status (S-F03) and, on a dev-only screen, the proposals on one project. There is no "my projects" list, no hires, no spending and no time-to-hire.
- **General users.** Request counts only. There are no in-app notifications or unread count, no saved items and no activity feed.
- **Administrators.** Everything is through generic Frappe Desk lists: no dashboard, report, Number Card or scheduled aggregate. Integration failures land in the Error Log one by one, and search is not logged at all.

## B. Gamification coverage

- **Points and levels:** none. The only "points" on the platform are a paid wallet (G-X04).
- **Achievements and badges:** none earned. One real, server-derived trust badge (partner). One unused demo component.
- **Challenges and milestones:** none in the marketplace. The host app's daily gift is the only time-boxed reward.
- **Progress dashboards and rewards:** only the profile-completion bar and checklist (client-side, dev-only).
- **Reputation and leaderboards:** none. Reviews were deliberately removed, and ranking is a sort by self-reported experience.
- **Abuse prevention:** good for requests (session identity, rate limit, duplicate guard, row lock, party checks, non-enumerable ids). Weak for proposals (no rate limit, no project-open check, no lock). Broken for verification (self-grant).

## D. Proposed MVP

A realistic first release, built on what already works (request workflow, row-level permissions, Version log, Error Log, e-mail queue):

1. **Trust fixes (P0 #1–#8)**, with no new features. This removes misleading data before anything is measured.
2. **Request lifecycle timestamps (#9)** on Inquiry only, set inside `api/workspace.py` (`submit_request`, `respond_request`, `set_request_status`), plus a small one-off patch that back-fills `first_responded_at` from Version history where possible.
3. **Provider "إحصائياتي" card** on the existing inbox, via one whitelisted `provider_stats()` that returns, for the caller's profile and the last 90 days:
   - requests received by all 6 statuses;
   - response rate = answered within 48h / received;
   - median first-response time;
   - acceptance rate = Accepted / (received − Cancelled).
   Each value appears only after a minimum of 5 requests. Visible to the owner only.
4. **Profile views (owner-only)** via a server-side counter written in `get_accountant` when called from the gateway. Use a daily-deduped `(profile, visitor_hash, date)` row, exclude the owner, and aggregate nightly. No public display yet.
5. **Server-side profile completeness**, returned with `get_my_profile` and used by both MyProfile and the admin distribution.
6. **Admin**: one Desk dashboard with Number Cards (published profiles, pending verifications, services, open projects, requests by status this week, Error Log "Marketplace*" in the last 24h).

Explicitly **out of the MVP**: points, levels, leaderboards, challenges, money metrics, public reputation scores. Revisit achievements after reviews exist and the data has been reliable for a few months.

## G. Privacy and permissions

- **Likely exposure of identities to Guests (verify first).** Profiles, Services and Projects grant Guest read at permlevel 0 (`marketplace_profile.json`, `marketplace_service.json`, `marketplace_project.json`). The standard `owner` field is not covered by the permlevel-1 protection that hides `user` and `client`, and the app relies on `owner` equalling the user's e-mail (`APP/api/docs.js:107-116`). Profile `company` (Link to the accounting Company) is also permlevel 0. **Recommendation:** remove Guest DocPerm and serve public reads only through `MP/api/public/*` (which already uses allowlisted serializers, `MP/services/serializers.py`), or confirm the fields are stripped. The app's directory reads (`APP/api/directory.js`) would then switch to the public endpoints.
- **Verification status** is readable by Guests through `/api/resource` (permlevel 0), contrary to `README.md`. Acceptable if it is meant to be public once moderator-controlled; otherwise move it to permlevel 1.
- **Future view and visitor tracking.** Store hashed, rotating visitor ids, never raw IPs. Exclude the owner. Show providers aggregates only, never who viewed them. Keep a retention limit (e.g. raw events 90 days, aggregates indefinitely).
- **Search logs.** Queries can contain tax or personal details. Store truncated or normalised text, never the user id for guests, with short retention. The embedding client already avoids logging query text (`MP/services/embedding_client.py:59-60`). Keep that rule for analytics.
- **Response rate, acceptance rate and repeat clients** are business-sensitive. Show them to the owner first, and make public display opt-in with minimum sample sizes.
- **Client data.** Requester contact details are correctly given only to the provider of that request (`MP/api/workspace.py:83-85`). Keep any client statistic (hires, spending) private to the client, and expose only aggregate counts on project pages.
- **Partner badge** reveals a commercial relationship with eDariba. Label it as such and do not present it as a quality signal.
- **Rankings or leaderboards** (if ever built): opt-in, banded rather than exact positions, and never based on spending.
